1. What is DSPy?

DSPy is a framework from Stanford that treats prompts as learnable programs rather than hand-written strings. Instead of manually tuning a prompt by trial and error, you define what you want the LLM to do (the Signature), wire it into a Module, write a metric, point it at labelled examples, and let the optimizer search for the best prompt automatically.

💡

The key insight: DSPy doesn't change model weights. It searches over the discrete space of (instruction text, few-shot example subsets) and picks the combination that scores highest on your metric. No gradient descent — just structured search.

Traditional approach

  • Write a long, detailed system prompt
  • Test it manually on a few examples
  • Tweak wording when you find failures
  • Repeat indefinitely
  • No systematic way to know if you're improving

DSPy approach

  • Define the task as a Signature
  • Collect labelled examples
  • Write a metric (what "good" means)
  • Run the optimizer — it searches automatically
  • Measure improvement on a held-out test set

2. Core Concepts

Signature — what the task is

A Signature declares the task's inputs and outputs. The docstring becomes the instruction to the LLM. DSPy can rewrite this during optimization.

class RedFlagClassifier(dspy.Signature):
    """Classify whether a candidate description extracted from a regulatory
    document is a genuine AML red flag (observable suspicious behavior) or
    not (compliance guidance, regulatory instruction, case narrative, etc.)."""

    description: str = dspy.InputField(
        desc="A candidate red flag description extracted from a regulatory document."
    )
    is_red_flag: bool = dspy.OutputField(
        desc="True if observable suspicious behavior; False if compliance guidance."
    )

Module — how the task is called

A Module wraps the Signature and controls how the LLM is prompted. Two common options:

Predict

Direct classification

Description → Is Red Flag

Faster and cheaper. Works well when the boundary is clear.

dspy.Predict(RedFlagClassifier)
ChainOfThought

Reason then classify

Description → Reasoning → Is Red Flag

More accurate on subtle cases. Costs one extra field per call. This is what we use.

dspy.ChainOfThought(RedFlagClassifier)

Optimizer — how the prompt is improved

We use BootstrapFewShotWithRandomSearch. It:

  1. Runs the current module on training examples
  2. Collects traces where the model got the right answer — these become candidate few-shot demos
  3. Randomly samples different subsets of those demos (8 candidate programs)
  4. Scores each candidate against the training set using your metric
  5. Returns the highest-scoring combination of instructions + demos

Metric — what "good" means

Our metric penalizes false positives more than false negatives, reflecting the goal of eliminating compliance guidance from the output:

def precision_weighted_metric(example, prediction, trace=None) -> float:
    if label == predicted:   return 1.0    # correct
    if predicted and not label: return -0.5 # false positive — penalise harder
    return 0.0                              # false negative

3. Where DSPy fits in the extraction pipeline

The full extraction pipeline for each document is:

Step 1 Extract
LLM reads the PDF/URL and pulls out candidate indicators
→
Step 2 Shape
Rewrites descriptions — adds noun subjects, merges dependent sentences
→
Step 3 Verify ← DSPy
Classifies each candidate as genuine red flag or false positive
→
Step 4 Validate & Write
Schema validation, regulator inference, YAML output

DSPy is involved only in Step 3. It is offline — it runs once during optimization and produces a data/verifier_prompt.json file. At runtime, the verifier makes a single direct OpenAI API call per document using that saved prompt. DSPy itself is not involved at inference time.

⚠️

Online vs Offline: DSPy runs offline (once, to find the best prompt). The production verifier runs online (every extraction), using the saved result. You only need uv sync --extra optimize to run optimization — not for everyday extractions.

4. Our DSPy setup

# scripts/optimize_verifier.py

# 1. Configure the LLM
lm = dspy.LM("openai/gpt-5.4-nano")   # cheap model for optimization search
dspy.configure(lm=lm)

# 2. Create the module (ChainOfThought = reason before classifying)
program = RedFlagCoT()   # wraps dspy.ChainOfThought(RedFlagClassifier)

# 3. Run the optimizer
optimizer = dspy.BootstrapFewShotWithRandomSearch(
    metric=precision_weighted_metric,
    max_bootstrapped_demos=4,    # up to 4 demos bootstrapped from training
    max_labeled_demos=4,         # up to 4 demos from human-labelled examples
    num_candidate_programs=8,     # try 8 different demo subsets
    num_threads=4,
)
optimized = optimizer.compile(program, trainset=train_set)

# 4. Save — this is what the production verifier loads
optimized.save("data/verifier_prompt.json")

Model choice

gpt-5.4-nano is used for optimization because the search runs ~700 LLM calls (8 candidates × 88 examples). A cheap model keeps the one-time cost manageable. The production verifier defaults to gpt-4o-mini.

Train / test split

88 labelled examples are split 70/30. The optimizer sees only the 70% training set. The 30% test set is used after optimization to measure real-world improvement.

5. The optimization loop

Input

  • 88 labelled examples
    (description + flag + reasoning)
  • 70% train / 30% test split
  • Precision-weighted metric
  • Signature + ChainOfThought module
→

BootstrapFewShotWithRandomSearch

  • Run module on training examples
  • Collect traces where prediction = label
    (these become candidate demos)
  • Randomly sample 8 different demo subsets
  • Score each subset on training set
  • Pick highest-scoring program
→

Output

  • Optimized instructions
  • Best few-shot demo set
    (with reasoning traces)
  • Saved to verifier_prompt.json
  • Test set metrics reported
🔍

Bootstrap = self-generated labels. When DSPy runs the current program on training examples and the model gets it right, it saves that reasoning trace as a "bootstrapped demo". This is how it creates the few-shot examples — not from scratch, but by keeping the traces that already work. Human-labelled reasoning overrides bootstrapped reasoning when present.

6. Labelled data and reasoning

Our labelled data lives in data/source/labelled/. Each YAML item has the standard red flag fields plus flag (True/False) and optionally reasoning.

Without reasoning — DSPy bootstraps its own

- id: 042-01
  description: >-
    Transactions or customers connected
    to jurisdictions under OFAC sanctions.
  flag: True

With reasoning — DSPy uses yours directly

- id: 048-01
  description: >-
    The organization conducts an OFAC
    risk assessment in a manner...
  flag: False
  reasoning: >-
    This describes what the institution
    must do, not observable suspicious
    behavior. It is a compliance
    program obligation.
✅

Why reasoning on False examples matters most. The hardest classification problem is distinguishing "looks like a red flag but is actually a regulatory instruction". Human-written reasoning on these edge cases gives DSPy precise signal about the failure mode, rather than letting it guess from the label alone. Currently 52 of 96 examples have human reasoning — all the False cases.

In optimize_verifier.py, examples with reasoning are loaded as labeled demos with the full chain-of-thought trace included. DSPy treats these as higher-quality signal than bootstrapped traces:

kwargs = {
    "description": item["description"],
    "is_red_flag": bool(item["flag"]),
}
if item.get("reasoning"):
    kwargs["reasoning"] = item["reasoning"]   # human trace → labeled demo

ex = dspy.Example(**kwargs).with_inputs("description")

7. What the optimized prompt looks like

DSPy doesn't just add examples to our handcrafted prompt — it replaces the instructions with something it found worked better, and adds its own few-shot demos with reasoning traces. Here's what our actual data/verifier_prompt.json contains:

Instructions — simplified dramatically

Handcrafted (our prompts.py)

You are an AML compliance expert...

## What IS a red flag?
A red flag is a description of suspicious,
observable behavior...

## What is NOT a red flag?
- Compliance program guidance...
- Regulatory directives...
- SAR filing instructions...
[8 more exclusions]

## Classification rules
1. Does it describe observable behavior?
2. Is it reusable?
3. Could a TM system detect this?
4. Does it stand alone?

If ALL four answers are yes → flag: true
...

DSPy-optimized (verifier_prompt.json)

Classify whether a candidate description
extracted from a regulatory document is a
genuine AML red flag (observable suspicious
behavior) or not (compliance guidance,
regulatory instruction, case narrative,
etc.).

One sentence. DSPy found that detailed rules were less useful than concrete examples with reasoning.

Demos — the real value

DSPy selected 4 few-shot examples from the training set. These appear in every verification call:

True Demo 1 — bootstrapped (DSPy generated reasoning)

Description
The use of shell companies or other legal entities and arrangements to avoid detection

Reasoning
Using shell companies or other legal entities/arrangements to avoid detection is an observable, suspicious behavior that indicates potential attempts to evade regulatory scrutiny and sanctions.

True Demo 2 — bootstrapped

Description
Conducted or facilitated significant trade with North Korea

Reasoning
Actual facilitation or involvement in significant trade with North Korea is an observable high-risk activity. A compliance officer could detect and flag this based on transaction and trade records.

False Demo 3 — labelled (no reasoning) — subtle boundary case

Description
Special attention to business relationships and transactions with the DPRK, including DPRK companies, financial institutions, and those acting on their behalf

This looks like a red flag about DPRK exposure — but it is a regulatory instruction telling institutions what to watch for, not an observation of suspicious behavior. DSPy found this boundary case from the labelled data.

True Demo 4 — labelled

Description
Any customers that may be involved in the sale, supply, or transfer of the specified items to Russia or to jurisdictions previously identified as posing a high risk of Russian sanctions evasion.

8. How the optimized prompt is used in production

Once data/verifier_prompt.json exists, build_verification_prompt() in prompts.py loads it automatically. The production verifier makes a single direct OpenAI API call — no DSPy involved at runtime.

# prompts.py — simplified
def build_verification_prompt(descriptions, force_handcrafted=False):
    optimized = None if force_handcrafted else _load_optimized_prompt()

    if optimized:
        # Use DSPy-optimized instructions + inject demos as examples
        system_prompt = _build_optimized_system_prompt(optimized)
    else:
        # Fall back to handcrafted prompt
        system_prompt = _HANDCRAFTED_SYSTEM_PROMPT

    # Same user message either way: numbered list of descriptions
    user_prompt = f"Classify each candidate...\n[0] {desc0}\n[1] {desc1}..."
    return [{"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_prompt}]

Prompt selection at runtime

Condition Prompt used
verifier_prompt.json exists (default) Optimized DSPy instructions + demos
verifier_prompt.json missing Handcrafted prompts.py fallback
--prompt handcrafted flag Handcrafted even if JSON exists
--no-verify flag Skip verification entirely

9. Iterating when you find new failure modes

⚠️

Changing the handcrafted prompt in prompts.py has no effect while verifier_prompt.json exists. The optimized prompt completely overrides it. You must either delete the JSON file or re-run optimization after updating labelled data.

Recommended workflow for a new failure mode

  1. Update the handcrafted prompt in prompts.py to handle the new case. This is your human-readable specification.
    scripts/prompts.py → _HANDCRAFTED_SYSTEM_PROMPT
  2. Add the failure case to labelled data in data/source/labelled/ with flag and a reasoning field explaining why it is/isn't a red flag.
  3. Test the handcrafted prompt to confirm it handles the new case:
    uv run python scripts/eval_verifier.py --prompt handcrafted
  4. Re-run optimization to produce a new verifier_prompt.json:
    uv run python scripts/optimize_verifier.py
  5. Compare prompts to confirm the optimized prompt is better:
    uv run python scripts/eval_verifier.py --prompt handcrafted
    uv run python scripts/eval_verifier.py --prompt optimized

Key files at a glance

File Purpose When to edit
scripts/prompts.py Handcrafted verification prompt — human specification When you find a new failure mode
data/source/labelled/ Labelled examples with flag + reasoning Add new examples for every failure mode
scripts/optimize_verifier.py Runs DSPy optimization — one-time offline After adding labelled data
data/verifier_prompt.json DSPy output — optimized instructions + demos Never edit manually; regenerate via optimizer
scripts/eval_verifier.py Measures precision/recall on labelled data After any change to prompt or labelled data
