redflag-mcp — Pipeline Walkthrough

This document explains, step by step, what each part of the redflag-mcp repository does. The project ingests AML (Anti-Money Laundering) regulatory documents, extracts red flag indicators using LLMs, stores them in a searchable corpus, and serves them through an MCP server that compliance officers can query.

One-line summary. A regulatory PDF/web page goes in — structured, validated, embedded red flag records come out and become queryable over MCP.

End-to-end data flow

Phase 1 — Source acquisition

Get regulator-published material onto disk so it can be processed.

1a. scripts/harvest_sources.py — bulk catalog download

batchidempotent

uv run python scripts/harvest_sources.py red_flag_sources/Global_AML_CFT_Sanctions_Red_Flag_Catalog.csv
  • Reads the Direct URL column from a catalog CSV row by row.
  • Classifies each URL as PDF or web page via classify_url().
  • PDFs → downloaded with a browser-like user agent into red_flag_sources/pdf/.
  • Web pages → fetched through the Jina Reader API (https://r.jina.ai/<url>) which returns clean markdown; saved into red_flag_sources/markdown/.
  • Every download appends an entry to red_flag_sources/sources.yaml — the canonical "where did this file come from" record. Deduplication is by URL.
  • Files are named with a zero-padded serial (043.pdf, 061.md) assigned by next_serial().

1b. scripts/pipeline.py — URL-by-URL workflow

Same building blocks as harvesting, but driven by a plain-text URL list (one URL per line) and bundled with the extraction step:

# end-to-end: download + extract + manifest + registry refresh
uv run python scripts/pipeline.py run urls.txt

# two-step: download first, inspect captures, then extract
uv run python scripts/pipeline.py download urls.txt
uv run python scripts/pipeline.py extract

Useful flags: --force (bypass dedup), --parallel N, --no-verify, --prompt handcrafted.

Archive folders are skipped. red_flag_sources/pdf/archive/ and red_flag_sources/markdown/archive/ are excluded by virtue of non-recursive glob("*.pdf") / glob("*.md") in discover_sources().

Phase 2 — Extraction

2a. scripts/extract.py

The heart of the pipeline. Reads PDFs (via pdfplumber) or Jina markdown captures, sends the full document text to an LLM with the extraction prompt, and parses out a list of candidate red flags.

Per-source flow (process_one)

  1. Resolve slug from the filename via the registry — e.g. 007_employee_retention_credit_fraud.pdf → "007_employee_retention_credit_fraud".
  2. Skip-if-exists check against data/source/.extracted_sources.yaml, unless --force.
  3. Text extraction: extract_text_from_pdf() walks all pages; extract_text_from_markdown() strips the Jina frontmatter.
  4. LLM call with build_extraction_prompt() from scripts/prompts.py.
  5. Verify (LLM #2) — drops false positives. See Phase 3.
  6. Shape (LLM #3) — rewrites grammar so every description begins with a noun subject. See Phase 3.
  7. Validate each candidate against the RedFlagSource Pydantic model and write to data/source/<slug>.yaml.
  8. Append a manifest entry to .extracted_sources.yaml.

The extraction prompt (scripts/prompts.py :: build_extraction_prompt)

The prompt is the most important piece of business logic in the project. It tells the LLM:

  • What a red flag is — observable customer/transaction behavior, not compliance-program text.
  • Explicit-section precedence — if the document has a "Red Flags" / "Risk Indicators" heading, only extract from there. Otherwise scan the whole document.
  • Reusable-indicator test — reject named persons, named companies, one-off facts.
  • Compliance-guidance exclusion — reject anything describing what an FI should do (training, audit, recordkeeping, etc.).
  • One-bullet-one-flag rule — do not split sentences inside a single bullet.
  • Per-field metadata guidance for every output field (product_types, industry_types, customer_profiles, geographic_footprints, regulator, issued_date, risk_level, category, typology_family, transaction_patterns, key_terms), each anchored to a controlled vocabulary from config.py.
  • Four worked examples — correct vs. wrong extractions.

Phase 3 — Verification & shaping

3a. Verification — remove false positives

verify_red_flags() in extract.py sends each candidate description to a second LLM call that classifies it as a genuine red flag (true) or not (false). Candidates marked false are dropped.

Two prompt variants:

VariantSourceWhen used
Handcrafted_HANDCRAFTED_SYSTEM_PROMPT in scripts/prompts.pyFallback; forced with --prompt handcrafted
DSPy-optimizeddata/verifier_prompt.jsonAuto-loaded if present (default)

3b. Shaping — normalize grammar

shape_red_flags() sends surviving descriptions to a third LLM call that:

  • Ensures each description starts with a concrete noun subject ("Customers...", "Transactions...").
  • Merges dependent explanatory sentences ("Such...", "Similarly...") back into the preceding sentence.
  • Strips one-off names or case facts that slipped through.
  • Generalizes case-specific dollar amounts ("$100M stolen" → "large sums (e.g., $100M) stolen") so the indicator becomes reusable.
Order matters. The pipeline runs extract → verify → shape so shaping LLM calls are not spent rewording false positives that verification would drop.

Phase 4 — Registry & manifest

4a. scripts/build_registry.py

Builds red_flag_sources/registry.csv — a unified audit ledger combining:

  • Catalog CSVs (the canonical list of intended sources)
  • sources.yaml (what was successfully downloaded)
  • data/source/.extracted_sources.yaml (what was successfully extracted)
  • YAML files in data/source/ (the final, structured red flags)

Each registry row gets a status: extracted, downloaded, or not_downloaded. This file drives deduplication in pipeline.py and answers "how much of the catalog have we processed?"

4b. scripts/build_sources_registry.py

A narrower variant that just rebuilds sources.yaml from disk by re-inspecting downloaded files. Used to repair drift between filesystem and registry.

4c. scripts/review_markdown_sources.py

Interactive review tool for Jina markdown captures, used before extraction to weed out junk pages (404 captures, navigation-only stubs).

Phase 5 — Ingestion (vector store)

scripts/ingest.py — load YAML into LanceDB

uv run python scripts/ingest.py
  1. Discover every *.yaml under data/source/.
  2. Parse each into RedFlagSource via Pydantic.
  3. Auto-tag missing metadata — if any of the metadata fields are blank, call OpenAI (gpt-4o-mini) with the tagger prompt to fill them. Free-form values outside the controlled vocabularies emit a warning.
  4. Embed the description with nomic-embed-text-v1.5:
    • Documents prefixed with "search_document: " (768-dim vector, L2-normalized).
    • Queries later get the "search_query: " prefix — this asymmetric scheme is required by the Nomic model.
  5. Upsert into the red_flags table in data/vectors/red_flags.lance. Schema is PyArrow with vector + all metadata fields including list-typed typology_family, transaction_patterns, key_terms.
  6. Optional write-back: --write-back-yaml serializes enriched records back to source YAMLs so the enrichment becomes durable.
Why this is a separate step. The Nomic model is ~275 MB and downloads on first call. Doing it during ingestion (not at MCP server startup) avoids Claude Desktop connection timeouts.

Phase 6 — Corpus packaging

scripts/build_corpus.py

Builds a versioned, hash-pinned SQLite FTS5 package for offline / hosted deployment that does not require Python, OpenAI keys, or the embedding model.

  1. Reads all source YAMLs.
  2. Creates a SQLite database with FTS5 (full-text search) tables over descriptions and key terms.
  3. Bundles the DB + manifest.json (version, SHA256, source list, schema version) into a ZIP package.

scripts/verify_corpus.py

Validates a packaged corpus ZIP: schema version, manifest integrity, hash match, record count. Run before deploying.

Runtime activation: src/redflag_mcp/corpus_install.py

At server startup in hosted-corpus mode, the server fetches the configured package URL, verifies the SHA256, extracts it to a cache directory, and opens the SQLite store. The release index (release_index.json) supports auto-update to a newer version.

Phase 7 — MCP server & tools

src/redflag_mcp/server.py

Builds a FastMCP server with three runtime modes:

ModeStorageEmbedding model loaded?Use case
VECTOR_DEV (default)LanceDB at data/vectors/Yes — for semantic searchLocal dev with full vector search
LOCAL_CORPUSPackaged SQLite FTS5NoAir-gapped institutional deployment
HOSTED_CORPUSPackaged SQLite FTS5 (fetched)NoPublic hosted connector at /mcp

Transport switches by env var MCP_TRANSPORT=stdio|http. Critical: in stdio mode, stdout is the JSON-RPC channel; any print() would corrupt the protocol — the code uses logging exclusively.

src/redflag_mcp/tools.py — the seven MCP tools

ToolWhat it does
classify_red_flag_requestTriage helper. Given a user request, recommends whether to use search_red_flags or filter_red_flags, and what filter values to apply. Use this before searching for vague requests.
search_red_flagsSemantic search. Embeds the query, retrieves top-k by vector similarity (LanceDB) or BM25 ranking (FTS5). Supports metadata filters.
filter_red_flagsPure metadata filter, no semantic ranking. For requests like "all red flags from FCA" or "all sanctions-evasion red flags in trade_finance".
get_red_flagFetch one red flag's full record by ID.
list_filtersReturns the valid values for every filterable field — the controlled vocabularies, plus actually-observed values.
list_sourcesSummary of every regulatory source represented in the corpus (one row per regulator document).
get_sourceDetail view for one source: citations, aggregate metadata, related red flag IDs, snippets.

Supporting registrations

  • resources.py — registers MCP resources: source_catalog (JSON dump of all sources) and source_detail/{source_id} for client-side preview.
  • prompts.py (server-side) — registers MCP prompts for guided querying.
  • http_app.py — ASGI app for HTTP transport; used by hosted deployment.

Phase 8 — Evaluation & optimization

scripts/eval_verifier.py

Measures the verifier's precision, recall, F1, and accuracy against hand-labelled YAML files under data/source/labelled/. Also reports a "no verifier" baseline (everything classified true) for comparison.

scripts/optimize_verifier.py

Uses DSPy to programmatically improve the verifier prompt:

  • BootstrapFewShotWithRandomSearch (default) — learns good few-shot demonstrations to attach to the handcrafted instructions.
  • MIPROv2 (--optimizer mipro) — jointly optimizes instructions and demos. More LLM calls, often better.

Output: data/verifier_prompt.json with optimized instructions + few-shot demos. The verifier auto-loads this if present.

Requires the optional optimize extra: uv sync --extra optimize.

scripts/evaluate_retrieval.py

Small benchmark suite for the retrieval layer: loads a query set, runs each against a corpus package, and reports recall@k.

Controlled vocabularies (src/redflag_mcp/config.py)

These are suggested — the prompt prefers them but allows free-form values when nothing fits. Free-form values are logged as warnings so the vocabulary can evolve.

  • RISK_LEVELS — high, medium, low
  • PRODUCT_TYPES — institution-facing channels (depository, wire_transfer, correspondent_banking, …)
  • CATEGORIES — primary AML typologies (structuring, sanctions_evasion, …)
  • INDUSTRY_TYPES — customer industries (real_estate, manufacturing, casinos, …)
  • CUSTOMER_PROFILES — archetypes (politically_exposed_person, money_services_business, …)
  • GEOGRAPHIC_FOOTPRINTS — regions and sanctioned countries (iran, syria, east_asia, …)
  • TYPOLOGY_FAMILIES — broader-than-category families (narcotics_proceeds, …)
  • TRANSACTION_PATTERNS — observable patterns (structuring, bulk_cash_smuggling, …)
  • REGULATORS + REGULATOR_JURISDICTIONS — issuing authorities and their country codes
  • URL_DOMAIN_TO_REGULATOR — deterministic regulator inference from a source URL's domain (e.g. www.fincen.gov → FinCEN). Overrides the LLM's regulator guess when the domain is recognized.

Common operator workflows

Add a new regulatory document

# 1. Drop the URL into urls.txt
echo "https://www.fincen.gov/new-advisory.pdf" >> urls.txt

# 2. Run the pipeline (download + extract + verify + shape)
uv run python scripts/pipeline.py run urls.txt

# 3. Review the generated YAML in data/source/<NNN>_<slug>.yaml

# 4. Re-ingest so the new flags are searchable
uv run python scripts/ingest.py

Re-extract everything after a prompt change

# Forces re-extraction even for sources already in .extracted_sources.yaml
uv run python scripts/pipeline.py extract --force --parallel 4

Ship a new hosted corpus

uv run python scripts/build_corpus.py
uv run python scripts/verify_corpus.py data/corpus/<package>.zip
# Publish the package + update release_index.json on the hosted bucket

Run the MCP server locally

# stdio (Claude Desktop / Claude Code)
uv run python -m redflag_mcp

# HTTP transport (OpenAI agents, web clients)
MCP_TRANSPORT=http MCP_PORT=8080 uv run python -m redflag_mcp
